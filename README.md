# 采购合同审查 Agent：把每条风险算成钱

[![CI](https://github.com/kennywu411-dev/contract-review-agent/actions/workflows/ci.yml/badge.svg)](https://github.com/kennywu411-dev/contract-review-agent/actions/workflows/ci.yml) ![Python 3.12](https://img.shields.io/badge/python-3.12-blue) ![License: MIT](https://img.shields.io/badge/license-MIT-green)

签采购合同之前，它逐条找出对我方不利的条款，并把每条能算的风险换算成金额：**这份合同不改，最坏多花多少钱，先谈哪一条。**

- **给谁用**：没有专职法务的采购人员和采购负责人。
- **解决什么**：合同审查工具通常只给"高 / 中 / 低"。十条意见里先谈哪条、值不值得为它卡住合同，等级回答不了，金额可以。
- **特色**：大模型只负责读条款、把数字抄出来，金额全部由规则代码按公式计算。每个金额都带算式、用到的合同原文和假设；抄出来的数字逐个核对原文，核对不上不出金额；算不了的标"无法量化"。
- **关键数字**（60 份没参与调试的构造采购合同，各跑两次）：
  - 133 个应有金额的测算项，算对 133 个和 132 个；给出的金额全部分毫不差，没有一个错的金额。
  - 26 个算不了的条款（背靠背付款、按实际损失计的违约金等）全部标成"无法量化"，没有硬算。
  - 对照：让同一个模型直接算金额，准确率差不多（97.0%–99.2%），但只有 77%–81% 分毫不差，同一份合同跑两次约有 9% 的项目结论不一样，错的时候是差 10 倍的金额、没有任何提示。

**[在线回放](https://kennywu411-dev.github.io/contract-review-agent/)**：6 份合同的真实审查过程，前两份带金额测算。不用装环境，每一步工具调用、每条依据、每个金额的算式都能点开。

原有的审查能力不变，7 类合同都支持，采购是主打场景：

- 每条意见附依据原文，来源包括《民法典》、合同编通则解释、《民事诉讼法》、官方合同示范文本和本公司的审查规范，点编号就能看到高亮的条文。
- 单价通过 [MetricLens](https://github.com/kennywu411-dev/metriclens) 的只读 MCP 查供应商台账，和历史成交价比较。
- 看不出我方是甲方还是乙方时，先反问。
- 依据核实不了的意见不删除，标为"转法务复核"。

## 金额测算

一份 4 行标的的采购合同（`evals/contracts_v3.jsonl` 里的 v3-goods-12，构造）审完之后，汇总区是这样的：

```
按现在的条款签，最坏情况多花 ¥384,706.94
  不改就确定多花 ¥151,631.69 · 最坏情景下的敞口 ¥233,075.25

谈判优先级
1  第六条  定金超过法定上限 20% 的部分          ¥164,137.50
2  第一条  单价高于台账历史均价：本单多付        ¥124,920.00
3  第九条  违约金不对等：同样逾期，我方比对方多付  ¥68,937.75
4  第五条  付款条件的资金占用成本（未列为风险）    ¥26,711.69
```

点开第 3 项：

```
我方：合同总额 3,282,750 ×（日费率 0.1% × 30 天 = 3%）= 98,482.50；
对方：合同总额 3,282,750 ×（日费率 0.03% × 30 天 = 0.9%）= 29,544.75；差额 68,937.75 元
用到的数字：甲方逾期违约金日费率 = 0.1，来自第九条“甲方逾期付款的，每逾期一日，应当按合同总额的千分之一向乙方支付违约金，违约金总额不超过合同总额的百分之五十。”（其余 4 个数字略）
假设：双方各逾期 30 天、逾期金额按合同总额计（可配置）
```

公式和设计理由见 [ADR 014](docs/adr/014-金额测算.md)。

**怎么算**

| 测算项 | 算什么 | 性质 |
|---|---|---|
| 比价 | 每行标的的单价和供应商台账历史均价比，超过公司标准的行：（合同单价 − 均价）× 数量 | 不改就确定多花 |
| 付款条件的资金占用成本 | 预付款、定金、账期相对公司标准付款条件多占用的资金 × 年化资金成本率 | 不改就确定多花 |
| 违约金 | 双方各逾期 30 天时，我方比对方多付多少；超出公司上限多少（两个口径只计较大的） | 最坏情景下的敞口 |
| 定金 | 超过法定 20% 的部分 | 最坏情景下的敞口 |
| 质保金 | 低于公司标准的保障缺口；我方收款时算被占用的资金成本 | 敞口 / 确定多花 |

- 资金成本率、逾期天数、公司标准付款条件在 `data/tenants/<公司>/quant.toml`，每家公司一份。标准条件取自该公司的合同审查规范；**资金成本率（5%–8%）、30 天逾期、5% 质保金标准是假设**，页面上每个金额旁边都列出。
- 单方解除、检验期、管辖、保密、知识产权、自动续约、责任限制这些风险没有确定的数，标"无法量化"并说明原因。
- 没被报成风险的条款也会算。上面第 4 项：账期合规，审查没有报，但预付款加定金占了 55%，比公司标准多占用资金。

**评测**

评测集 v3：构造的采购合同，单价、账期、定金、违约金等参数由生成器随机取值，所以每项金额有标准答案；18 份是 2–5 行标的，一半用中文数字（"万分之五""四十五日"）。判定方式（金额误差 ≤ 1% 算对）在跑之前写好。调试用 60 份，另外 60 份留出集在规则冻结后才跑，各方案跑两次：

| 留出集 60 份（第一次 / 第二次） | 模型抄数 + 规则计算（产品方案） | 模型直接给金额（推理强度 low） | 模型直接给金额（high） |
|---|---|---|---|
| 金额正确（133 项） | 133 / 132 | 132 / 131 | 130 / 129 |
| 其中分毫不差 | 133 / 132 | 108 / 102 | 107 / 107 |
| 给了金额但错了（误差 > 1%） | 0 / 0 | 1 / 1 | 2 / 4 |
| 算不了的条款标成"无法量化"（26 项） | 26 / 26 | 26 / 26 | 26 / 26 |
| 抄出的数字正确（641 个） | 637 / 641 | 不适用 | 不适用 |
| 两次运行结论完全一样（300 项） | 299 | 274 | 271 |
| 单份花费 P50 / 模型耗时 P50 | $0.00053 / 2.6s | $0.00075 / 4.5s | $0.00087 / 5.4s |

- **准确率上两种做法没有显著差别**（配对检验 p ≥ 0.25）。Haiku 5.5 拿到写清楚的公式，直接算也有 97%–99%。
- 选规则计算的理由是另外几点：金额分毫不差、可以复现、带算式和出处；出错的方式不同：规则方案唯一的 1 处错是"核对不上，没给金额"，直接算的 10 处错里 8 处是给了一个错的金额，其中 6 处正好差 10 倍或 100 倍（405.86 元算成 4,059.73 元）。采购会拿着金额去谈判，错的金额比没有金额危害大。
- **第一版其实输了**：调试集第一次全量，规则方案 93.5%，直接算 97.8% 和 100%。12 处错里 9 处是同一个原因：模型把"乙方逾期的，双方另行协商"声明成"算不了"，规则照单全收。问题不在算术，在第一版只核对了模型抄的数，没核对它"算不了"的判断。修正全部加在规则一侧，提示词没改（[问题日志](docs/问题日志.md) P26）。
- 完整审查流程里（20 份 v3 合同，多 Agent 审查 + 金额测算）：45 个应有金额全部算对，29 个挂在了某条审查意见上，其余 16 个（主要是质保金和"合规但多占用资金"的付款条件）在汇总区单独列出。金额测算占单份花费的 5%（约 $0.0005），耗时 2.7 秒，和审查并行。
- 原有审查评测没有被拉低：同一份代码在 v1 全量上开、关金额测算各跑一次，检出率都是 100%，类型和依据都是 100%，精确率（高/中）68.4% 对 70.6%，干净合同误报都是 66.7%，回归门禁通过（p = 1.0）。审查的提示词和输出结构没有动，金额测算是另一次并行的模型调用。
- 数据是自己构造的，留出集和调试集出自同一个生成器。真实合同的写法更多（阶梯价、分期付款、外币），没有验证过。

## 审查结果

48 份构造合同，模型 Haiku 5.5。另报 28 份没有参与调试的留出集。

| 指标 | 单 Agent（全部 / 留出集） | 多 Agent，默认（全部 / 留出集） |
|---|---|---|
| 风险检出率（73 处） | 100% / 100% | 100% / 100% |
| 风险类型判对 | 97.3% / 96.4% | 100% / 100% |
| 依据引用准确率 | 97.3% / 96.4% | 100% / 100% |
| 意见精确率（高/中等级） | 76.1% / 82.4% | 82.3% / 84.6% |
| 干净合同误报（12 份） | 66.7% | 41.7% |
| 当事人空白时反问 / 多余反问 | 100% / 0% | 100% / 0% |
| 对我方有利的条款被误报 | 0% | 0% |
| 单份花费 P50 | $0.0038 | $0.0062 |

几点说明：

- 检出率已经到顶，说明 v1 里植入的风险偏显眼，真正拉开差距的是误报。所以又做了更难的 v2（见下一节）。
- 上表多 Agent 一列是 v2 改进之前的代码。改进后的默认版本（专职审查员逐项对照规范红线）在 v1 上是做金额测算的回归检查时才第一次跑：检出 100%，精确率（高/中）68.4% 和 70.6%，干净合同误报 66.7%，单份花费约 $0.0100。这是下一节"不漏报换来误报回升"的取舍在 v1 上的表现。
- 只有 12 份干净合同，误报率波动很大：同一份代码跑两次，单 Agent 是 66.7% 和 83.3%。
- 依据校验：用 Sonnet 逐条评判 122 条意见，理由里有无依据说法、却没有标转人工的意见从 6.6% 降到 0.8%，误拦 2.0%（[ADR 008](docs/adr/008-合同审查的输出结构与依据校验.md)）。
- 多轮追问：带上一轮审查历史时，"你列的第 k 条怎么改"答对 8/8，不带时 0/8。"换成乙方视角再看"6/6 切换正确。
- 长对话压缩：12 组 8 轮对话，结构化摘要和保留全部历史的正确率一样（98.8%），只留最近 2 轮掉到 75.0%。压缩后历史短了 32%，但总花费只降 1%，因为每轮的大头是合同全文和检索结果（[ADR 011](docs/adr/011-长对话上下文压缩.md)）。
- 和 DeepSeek 对比：检出、类型、依据持平，精确率低约 6 个点，单份花费约 2.4 倍。默认用 Haiku，DeepSeek 作为私有化部署的备选（[ADR 010](docs/adr/010-国产模型对比-DeepSeek.md)）。

全部数字、运行 ID 和测量条件见 [docs/numbers.md](docs/numbers.md)。评测的运行、配对统计、反馈汇总和看板由 [evalkit](https://github.com/kennywu411-dev/evalkit) 提供。

## 难评测集 v2

60 份长合同（每份 25–30 条），75 处风险分 5 类：藏在不相关的条款里、换一种说法、要两条合起来看、数值刚好越过规范红线，以及普通风险。30 份干净合同里放了刚好合规的数值、合法的免责和对我方有利的条款作为干扰（[ADR 013](docs/adr/013-难评测集v2.md)）。

| 指标（各跑两次） | 单 Agent | 多 Agent 初版 | 多 Agent 改进后（默认） |
|---|---|---|---|
| 检出率（75 处） | 96.0% / 97.3% | 89.3% / 88.0% | 100% / 100% |
| 跨条款组合 / 临界值 | 83–92% / 93–100% | 66.7% / 73.3% | 100% / 100% |
| 精确率（高/中） | 61.6% / 61.0% | 68.1% / 68.6% | 65.7% / 62.6% |
| 干净合同误报（30 份） | 90.0% / 70.0% | 53.3% / 53.3% | 76.7% / 83.3% |
| 单份花费 P50 | $0.0045 | $0.0066 | $0.0115–0.0118 |

初版多 Agent 按标题分工，定义条款没人审，定金和违约金被分到不同组，专职组也不拿数值去对照规范红线。改进后定义条款发给每个组，漏分的条款按关键词兜底，专职组逐项对照红线，两次都检出 75/75，代价是误报回升、花费约 1.75 倍。合同审查里漏报比误报代价大，所以默认用改进后的版本。

## 工作方式

```
合同全文 → 主审（判断立场、分派条款）┬→ 三个专职审查员并行 → 汇总去重 ┐
                                    └→ 金额测算（并行）：模型抄数字 → 规则核对原文 → 查台账均价 → 按公式计算 ┴→ 金额挂到意见上
          （单 Agent 模式：一个审查 agent 直接审全文，提交意见后做金额测算）

审查 agent（Haiku 5.5，工具循环最多 8 轮）
  search_docs         BM25 + bge-m3 向量 → RRF 融合 → bge-reranker 重排
                      范围：通用法规和示范文本 + 本租户规范，租户由会话决定，模型改不了
  run_sql             通过 MetricLens 只读 MCP 查台账，用同名 CTE 遮蔽，只能看到本租户的行
  ask_clarification   看不出我方是甲方还是乙方时反问
  submit_review       提交意见：条款、摘录、类型、等级、理由、修改建议、依据编号、是否转人工

依据校验：先核对点名的条文是否真的被检索到，再用 Haiku 逐条核对，依据不足就转人工
Web：合同高亮、意见卡片（金额、算式、假设）、汇总区（最坏情况合计、谈判优先级）、点编号看条文原文、多轮追问
```

- 金额测算是一次强制结构化输出的模型调用，只抄数字，不做计算。规则代码解析中文数字和比例、逐个核对原文、用固定的一句 SQL 通过 MCP 取台账均价、计算并写出算式。测算失败不影响审查意见（[ADR 014](docs/adr/014-金额测算.md)）。
- 一次审查通常两轮模型调用：第一轮并发发起 5–7 次检索和查表，第二轮提交全部意见。
- 每一步都记录输入输出、token、花费和耗时，Web 端可以逐步回放。
- 向量检索可以切换到 Milvus Lite，结果和 numpy 一致，但在这个规模下 numpy 更快，所以默认不切（[ADR 009](docs/adr/009-Milvus-Lite向量后端.md)）。

## 运行

需要 Python 3.12、[uv](https://docs.astral.sh/uv/)、Node 20+ 和 npm。

```bash
uv sync                                               # 约 1GB（torch、docling）
uv run cra ingest                                     # 下载法规和 7 份示范文本、解析入库，生成供应商台账库
npm --prefix web install && npm --prefix web run build   # 构建前端到 web/out
uv run cra serve                                      # http://127.0.0.1:8000，只监听本机，托管 web/out
```

需要 `ANTHROPIC_API_KEY`，写在环境变量或根目录 `.env` 里：

```
ANTHROPIC_API_KEY=sk-ant-...
```

- 第一次审查请求会下载 bge-m3 和 bge-reranker-v2-m3（共约 2.3GB）并建向量缓存，要等几分钟；想提前做好，运行 `uv run cra index`（可选）。
- 没有 MetricLens 时查台账自动用本地库；装了 MetricLens 的话用 `METRICLENS_DIR` 环境变量指向它的目录，`cra link-metriclens` 会把台账库链接进去。
- 示范文本来自市场监管总局合同示范文本库，网站标注了版权，所以原文只在本地使用、不进仓库，仓库里只有文本 id 和下载脚本。

评测（会调用 API，都有 `--max-cost` 预算上限）：

```bash
uv run cra eval-review --sample 20
uv run cra review-d4 <运行目录名>
uv run cra eval-review-dialog <运行目录名>
uv run cra eval-contract-retrieval --backend milvus   # 需要 uv sync --extra milvus
uv run cra eval-quant --evalset v3-holdout            # 金额测算：抄数 + 规则，对照模型直接给金额
uv run cra eval-quant --rescore <运行目录名>          # 用当前规则重算保存的模型输出，不调 API
```

测试：`uv run pytest -q`。没有运行 `cra ingest` 时，依赖法规语料的几个测试会自动跳过。

## 评测集

48 份构造合同，覆盖 7 类合同：工业品买卖、农产品买卖、加工承揽、仓储委托、数据委托处理、数据产品开发、数据供应。条款顺序参照官方示范文本，正文是自己写的。

- 36 份植入 1–3 处风险，11 类风险每类 6–7 处；12 份干净合同，其中 6 份含对我方有利的单方条款，用来测立场判断。
- 4 份当事人名称空白，用来测反问；6 处临界条款，用来测转人工。
- 每处风险都标了合法依据集合（法条和公司规范条号），依据准确率按集合自动判分。

生成：`uv run python scripts/make_contracts.py`；校验：`uv run pytest tests/test_contract_evalset.py`。

另有 v2 难评测集（60 份长合同）和 v3 采购金额测算集（调试集和留出集各 60 份采购合同，每项金额有标准答案，`scripts/make_contracts_v3.py`）。

## 早期场景

项目一开始做的是高校规章问答，检索（Recall@5 97.9%）、agent（引用命中 96.3%）、生成后校验（幻觉率 31.9% → 15.6%）和多轮记忆都在那个场景里验证过。后来考虑到合同审查更贴近企业的实际需求，换了场景，原因见 [ADR 007](docs/adr/007-场景变更为合同风险审查.md)。早期的数字保留在 [docs/numbers.md](docs/numbers.md) 和 ADR 002–005，不算作合同场景的效果。

## 局限

- 评测数据是自己构造的，有"自己出题自己考"的风险。缓解办法：每类风险用多种写法，agent 看不到植入规则，加入干净合同和干扰条款，另报留出集。
- 不构成法律意见，拿不准的条款由法务复核。
- 金额是按写明的公式和假设算出的测算值，不是预测：换一组资金成本率或逾期天数，结果就会变。金额测算只在构造的采购合同上评测过，真实合同的写法更多（阶梯价、分期付款、外币），没有验证。
- 只为本机演示设计：服务只监听 127.0.0.1，没有登录和权限体系，不能直接对外部署。
- 法规文本以下载时的版本为准。《民事诉讼法》2023 年修正版取自上海市发改委网站转载的全文。
