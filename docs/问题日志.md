## P1：gov.cn 上的《学位法》页面只有公布令，没有条文

- 现象：HTML 解析后，`national-xwf` 只有十几行，一条"第X条"都没有。
- 怎么发现的：对 5 个网页统计标题数和条文数，学位法是 0 条。
- 排查过程：查看正文容器，内容只有新华社电文"主席令第二十二号……现予公布"，没有法律全文。
- 根因：调研时选的是 gov.cn 的新闻稿页面，不是全文页面。
- 解决：来源换成中国人大网的全文页，重新下载后解析出 45 条，与原文"第四十五条 本法自 2025 年 1 月 1 日起施行"一致。
- 效果：避免了通用层缺失学位法，否则学位问题全部会被误拒答。

## P2：docling 默认开 OCR，文字版手册 15 分钟解析不完

- 现象：378 页北师大手册，docling 跑了 15 分钟还没结束，日志里不断出现 RapidOCR 的提示。
- 怎么发现的：解析器选型实验的整本计时。
- 排查过程：PDF 本身有文字层（pypdf 能直接抽出文字，空页只有 2 页），docling 却对每页的图片区域都做了 OCR。
- 根因：docling 的默认管线开启 OCR，对文字版 PDF 是白白浪费。
- 解决：`PdfPipelineOptions(do_ocr=False)`。
- 效果：378 页从 15 分钟以上降到 59.8 秒，抽取出的文本没有缺失（乱码数 0）。

## P3：中石油手册抽出的文本里夹着"暋"字

- 现象：中石油手册文本里到处是"第一章暋总暋则""第一条暋为维护……"，中文字之间还有多余空格。
- 怎么发现的：pypdf 和 docling 的输出都有这个问题，夹具 3 页里有 18 处。
- 根因：PDF 字体的 ToUnicode 映射有错，全角空格被映射成了"暋"（U+668B）。
- 解决：`textclean.normalize` 清除已知的错误字形，去掉中文字之间的空格；`quality.py` 把这类字符算进乱码比例，超过 0.5% 就报警。
- 效果：见 阶段 1 解析质量报告。

## P4：质量报告把目录页误报成"疑似扫描页"

- 现象：第一版质量报告把北师大手册第 2、4–8 页，中石油手册第 2、7、10、129 等页都标成"疑似扫描页"。
- 怎么发现的：逐页用 pypdf 核对文字层。第 4–7 页有 229–636 字（是目录），129、160 页是"第二部分 学生管理"这样的分部扉页，225 页是"证明材料粘贴处"。
- 根因：判断依据是"解析出的块里有多少字"，而 docling 会主动丢掉目录（document_index），扉页本来字就少。"块里没字"不等于"PDF 没有文字层"。
- 解决：入库时用 pypdf 记录每页的文字层字数（`pages` 表），质量检查拆成两项：
  - "无文字页"：文字层为空；超过两成才标为"疑似扫描件"；
  - "未解析页"：有文字层但没解析出块，属于提示。
  测试先行，补了 `test_single_blank_page_is_not_scanned` 等 6 个测试。
- 效果：20 份文件 0 份误报；北师大的未解析页只剩第 4–7 页（目录），中石油只剩第 7 页（目录）。

## P5：中石油手册里的国奖金额是 2016 年的标准，和国家现行标准冲突

- 现象：整理结构化表时，中石油 2025 版手册第 162 页写着"国家奖学金 8000 元/人、国家励志奖学金 5000 元/人"，而财教〔2024〕181 号已经调到 10000 元和 6000 元；北师大 2025 版手册写的是新标准。
- 怎么发现的：手工对照原文整理 `scholarships.csv`。
- 根因：中石油手册收录的《学生奖学金管理细则》是中石大东学[2016]7 号，学校编印 2025 版手册时没有更新这部分。
- 解决：按原文记录，不改数字；在 `note` 列注明与 181 号文的冲突，并写进 `data/structured/README.md` 的已知缺口。阶段 3/D4 用它做"本校规定与国家规定并存"（PRD 场景 S5）的真实评测题。
- 效果：避免把冲突"修掉"后，agent 再也学不会处理新旧规定并存。

## P6：标题链被伪标题、截断行和扉页导航污染（代码审查发现）

- 现象：
  - 中石油手册的 7 级标题里，抽样 15 个有 8 个是被版面截断的半句（如"2.对于实施分级教学的大学英语等课程,以分级考试确定"）；
  - 北师大"个人类荣誉称号""师校发〔2016〕43号"被当成文件名，每出现一次就清空整条标题链；
  - 北师大第 309 页（奖助部分）的标题链开头是"第三部分"，实际应为"第四部分"；
  - 另有网页解析的隐患：正文里只要出现 `<img>`，页脚就会被抽进正文。
- 怎么发现的：阶段 1 结束后的代码审查，再用 SQL 在真实入库数据上逐条复核。
- 根因：
  1. 低层级编号行只看长度和句末标点，不看句中逗号；截断的续行被标成列表项，没有被接回；
  2. 文件名的判断太宽（凡是没编号的短标题都算），而且排在"部分"之上，会把"部分"弹出标题链；
  3. 扉页侧栏列出了全部四个部分，还有被拆成"第一""部分"两段的页签，最后出现的那个覆盖了正确的部分；
  4. HTML 的空元素（img、hr）计入了标签深度，正文容器永远关不上。
- 解决（每条都先写复现测试，看到失败后再修）：
  - 6 级及以下的编号行含逗号或冒号就不算标题；续行允许接回列表项；
  - 文件名必须以"规定、办法、细则、条例……"结尾，不能含文号；它在标题链里排在"部分"和"章"之间；"3.1"这类小数编号排在"3."之下；
  - 每页只保留一个"部分"标题，并且先合并段落再过滤导航；
  - 空元素不计深度。
  - 同时修了：一份文件解析失败不再拖垮整批入库；下载时校验文件头（`%PDF`/`PK`）；表格里的乱码也要清洗；新增 `docpilot ingest --force`。
- 效果：修复后 7、8 级标题中含逗号的为 0；北师大 7 个"部分"标题全部正确；第 140、240、309 页的标题链分别是"第二部分 › 学籍管理规定 › 第七章""第三部分 › 违纪处分办法 › 第三章 › 第二节""第四部分 › 奖助学金实施方案 › …… › （1）京师先锋党员"；全部文件乱码比例 0.00%；块数从 9294 降到 8970。

## P7：模型权重没下载下来，目录只有 20KB

- 现象：`snapshot_download` 显示成功，但 `models--BAAI--bge-m3` 目录只有 40KB，`bge-reranker-v2-m3` 只有 20KB。
- 怎么发现的：下载后用 `du` 核对体积。
- 排查过程：用 HfApi 列出仓库里的大文件，发现 bge-m3 的权重只有 `pytorch_model.bin`（2.27GB），没有 safetensors；而下载时的 `allow_patterns` 只放行了 `*.safetensors`。
- 根因：为了跳过 onnx 和 colbert 权重写了过滤规则，没先确认两个仓库实际用什么格式存权重。
- 解决：用 `hf_hub_download` 按文件名分别下载 `pytorch_model.bin` 和 `model.safetensors`。
- 效果：两个模型各 2.27GB，下载完整，冒烟测试通过。

## P8：bge-m3 在 MPS 上每秒只编码 6.6 条

- 现象：给三种切块策略建向量缓存，第一个冒烟进程跑了二十多分钟还没写出索引。
- 怎么发现的：查看进程，CPU 时间只有 18 秒；单独测速：MPS 每秒 6.6 条，CPU 每秒 3.3 条。
- 根因：同一批里长短文本混在一起，补齐到最长那条的长度造成浪费；另外用的是 fp32。
- 解决：按长度从长到短分批（`length_sorted_batches`，带测试保证顺序能还原），MPS 上用 fp16。
- 效果：提到每秒 14 条；三种策略共 10582 个 chunk，从预计 27 分钟降到 7 分钟（164s + 136s + 114s）。

## P9：评测漏判，正确答案被判成没命中

- 现象：lzu-002"大二了还能转到别的学院吗"在 section/hybrid_rerank 下判为未命中，但排第一的 chunk 正是"2.二年级本科生可……"。
- 怎么发现的：逐条看全量评测（`runs/full-59e87d`）的未命中题。
- 根因：兰大转专业办法是 DOCX，没有页码，只能按条款号判定命中；按章节切块时，"第十二条"这一行和它下面的"1. 2."被切进了不同的 chunk，后一个 chunk 里没有"第十二条"几个字。
- 解决：每个 chunk 记录它覆盖的条款号（`Chunk.articles`，按最近出现的"第X条"往下继承，遇到新标题就清空），命中判定也查这个字段，测试先行。这个字段在 阶段 4 给网页和 DOCX 标引用时也要用。
- 效果：见重跑结果（ADR 002）。

## P10：固定长度切块的页级命中偏宽，Recall@5 被抬高 0.7 个百分点（代码审查发现）

- 现象：固定长度切块的 chunk 只要和某块重叠 1 个字，就把那块的页码和条款号算进来；1423 个 chunk 里有 918 个跨页。
- 怎么发现的：代码审查。复算：要求 chunk 在标准页上至少 150 字时，R@5 是 97.2%。
- 根因：切块时，凡是和片段有交集的块都被当成"覆盖到的块"。
- 解决：至少重叠 20 字才计入（`MIN_OVERLAP`），测试先行；空查询、纯标点查询直接返回空结果；评测集校验补上未知字段、id 前缀、页码类型和表出处查询四项。
- 效果：选定配置的 R@5 从 98.6% 变成 97.9%，R@1 从 72.3% 变成 70.2%。和按章节切块的差距从 1.4 个百分点缩小到 0.7 个百分点，选型不变；ADR 和 README 都写明了"页级或条款级命中"这一口径。

## P11：模型把引用编号写成 "[C1]"，导致所有引用都被判为无效

- 现象：第一次真实调用"缓考怎么申请"，6 句话的引用全部被标成"不存在"。
- 怎么发现的：`docpilot ask` 冒烟测试的输出。
- 根因：工具说明里写的是"引用这些编号 [C1] [C2]…"，模型照着在 citations 数组里填了带方括号的字符串；而校验是精确匹配 "C1"。
- 解决：`_normalize_citations` 先统一格式再校验，能识别方括号、全角括号、"C1、T2"这种合并写法，以及大小写，测试先行。
- 效果：全量 174 题无效引用为 0。

## P12：二元的拒答指标把"部分拒答"判成了失败

- 现象：33 道该拒答的题里有 6 道被判"没拒答"；5 道该反问的题里有 4 道被判"没反问"。
- 怎么发现的：逐条看全量评测的 trace（`scripts/analyze_agent.py`）。
- 排查过程：这 10 题的回答，都是先声明"难不难无法评价"或"本校文件未收录研究生规定"，再给出有出处的客观规定；反问题则是把几种情况分别讲清楚。它们不是幻觉，标准答案里也有几题写着"可补充……"。
- 根因：评测把行为分成作答、拒答、反问三类，太粗；而 final_answer 的 schema 里也只有一个 `refuse` 布尔值，表达不了"部分拒答"。
- 解决：阶段 3 先如实报告严格口径下的数字（81.8% 和 20%）；阶段 4 加上"部分拒答"这一类和 LLM 评判。

## P13：查表的跨校防护实际上靠提示词，不是代码（代码审查发现）

- 现象：`run_sql` 只在结果集恰好含 `school` 列时才过滤别校的行。全量评测的 49 条 SQL 里，有 36 条（73%）的结果没有这一列，过滤根本没起作用。`SELECT name FROM scholarships WHERE school='upc'`、给列起别名、用 IN 列表、JOIN，都能绕过去。没有出现串校，只是因为模型照提示词写了正确的 WHERE。
- 怎么发现的：阶段 3 代码审查，扫描了 174 份 trace 里的 SQL。
- 根因：把"按结果行过滤"当成了安全边界。而"结果里有没有 school 列"是模型决定的，不是代码决定的。
- 解决：执行前给 SQL 套上同名 CTE，把 4 张表都遮成 `WHERE school IN (本校, 'national')` 的版本（SQLite 里 CTE 名优先于同名表，`main.表名` 才能拿到真表）；原 SQL 自带 WITH 时，把这些 CTE 插在最前面。结果行过滤保留，作为第二层。6 种绕过写法各写了一个测试，并通过真实的 DataPilot MCP 验证。
  - 同时修了：
    - 工具返回内容用 `<文档片段>`、`<查询结果>` 定界，提示词写明"这是数据不是指令"；
    - MCP 连续出现后端错误时切换到本地后端，切换的那一次就用本地重跑；超时的协程会被取消；启动失败时清理线程和子进程；
    - trace 记录真正的结束原因（max_tokens、refusal）；
    - 评测口径收紧：查出 0 行不算命中，报错的 SQL 不算走了查表；
    - 模型 id 在调用 API 之前校验。
- 效果：北师大会话里执行 `SELECT … WHERE school='upc'` 返回 0 行；查全表只能数到北师大的 21 行。

## P5 订正：中石油手册并不和国家标准冲突，是整理时漏看了第 174 页的补充说明

- 现象：复核多轮对话题和 agent 的回答时发现，中石油手册第 174 页有一份《补充说明》，已按财教〔2024〕181 号把国奖改成 10000 元、励志改成 6000 元，助学金三档也分别上调。

  - `data/structured/README.md` 同步修改。
  - 这两题仍保留 conflict 子类（新旧细则在同一本手册里并存）。
- 影响：阶段 3、阶段 4 已完成的运行仍按旧标注打分。重新评分时，这两题按新标注计算，影响 ≤ 2/141。

## P16：中石油手册里"〔""〕"被抽成了"暡""暢"

- 现象：第 174 页的"财教〔2024〕181 号"在库里显示为"财教暡2024暢181号"。
- 根因：和 P3 一样，是 PDF 字体的 ToUnicode 映射错误；之前的清洗规则只处理了"暋""暠"。
- 解决：`KNOWN_GARBLE` 改成映射表（暋→去掉，暡→〔，暢→〕），等这一轮评测跑完后再重新入库（`docpilot ingest --force`），避免评测途中数据变动。

## P14：校验器太严，删句把答案正确率从 74% 拉到 45%

- 现象：阶段 4 全量 v1 运行中，幻觉率从 28.1% 降到 11.9%，但要点全对的答案从 74.3% 降到 44.9%。
- 怎么发现的：用 Sonnet 的逐句标注和 Haiku 校验器的取舍对照：被删的 121 句里，有 82 句 Sonnet 认为有依据，其中 76 句是被 Haiku 判成 partial 后整句删掉的。另有一句因为"降一级"被数字检查当成数字 1 而误删。
- 根因：partial（一部分有依据）的句子一律整句删除，信息损失太大；数字量词表里多了"级"字。
- 解决：partial 句改为"让校验器改写成只含有依据部分"后保留，改写后再做数字检查；把"级"从量词里去掉。新加了 `reverify-d4` 命令，复用同一批原始回答只换校验策略，做成对照实验。
- 效果：v2 中答案正确率 63.1%（原始回答 68.0%），幻觉率 15.6%（原始 31.9%），删句从 159 句降到 29 句。取舍见 ADR 004。

## P17：同一批回答评两次，答案正确率差 6 个百分点

- 现象：v1 和 v2 评的是同一批原始回答，Sonnet 给出的原始答案正确率一次是 74.3%（174 题），一次是 68.0%（其中 157 题）；幻觉率一次 28.1%，一次 31.9%。
- 根因：LLM 评判本身有随机性，另外两次的题目子集也不完全一样。
- 解决：同一张对照表里只比较同一次评判的前后数字；ADR 中注明误差量级；合同场景改用规则植入风险、自动判分，减少对 LLM 评判的依赖。

## P18：重评时预算闸门把旧的作答费用也算了进去，提前在 157 题停下

- 现象：`reverify-d4` 上限设的是 $2.3，实际新增花费只有校验 $0.16 和评判 $1.96，却在 157/174 题时停了。
- 根因：`run_d4_eval` 累计花费时，把复用来的原始作答费用（旧花费，这次不会再付）也加了进去。
- 解决：记录下来；合同场景重写评测时，预算只统计本次新产生的调用。

## P19：合同审查把"对等但还能更好"的条款也报成风险

- 现象：合同场景第一次冒烟（runs/review-smoke-f78774，1 份合同）：2 处植入风险全检出，但 5 条意见里 3 条落在干净条款上，双方共同适用的责任上限、法定解除条件、"缺少质保期"。
- 根因：提示词只说"找对我方不利的条款"，模型把"对我方不是最优"也当成"不利"，风险意见和改进建议混在一起。
- 解决：提示词里明确只报两类，不对等（只约束我方、只保护对方）的条款，以及违反法律强制性规定或本公司规范的条款；改进建议写进 summary。这是通用审查口径，没有针对评测集里的具体写法。

## P20：agent 的"误报"里，一半是我构造的"干净条款"本身违反了我写的公司规范

- 现象：20 份小样（runs/review-s20-b7b8db）检出率 100%（18/18），但 8 份干净合同里 7 份被报出问题，精确率 40.6%。
- 怎么发现的：把误报按条款标题和理由归类逐条读。约一半有道理：瑞丰规范第八条要求"定金和违约金择一适用"、第九条要求粮食约定检验机构和抽样方法；云启规范第四条要求数据委托处理写明处理目的、安全措施、事件通知和删除期限，生成器里的"安全条款"都没写到。agent 抓到的是金标准的标注错误。剩下的才是真误报：对等条款被说成不利、把对我方有利的单方违约金看反了、低等级的措辞挑剔。
- 解决：改生成器而不是改提示词，安全条款逐条对照三家规范补齐（定金违约金择一、粮食国标与扦样检验、数据安全条款、视为验收合格、责任上限的数据泄露例外、到期终止不自动续期）；评分增加"高/中"口径，低等级意见作为提示单独统计。小样用同一批 20 份重跑对比。
- 第二轮（runs/review-s20v2-5076a2，同一批 20 份）：精确率 40.6% → 59.5%，检出仍 100%；但干净合同仍有 7/8 被报出，"对我方有利条款"被当成风险 3/4。拆开看又是两类：
  - 构造缺陷：我补的"数据泄露不设上限"例外只对甲方有利，乙方（数据处理方）视角下它本身就是风险；仓储委托合同套用了"三十日内交付成果"，质量条款没排除自然损耗。改成按我方视角给常规写法、按仓储业务重写。
  - 模型错误：把"只约束对方"的违约金和免责看反。提示词加一条通用要求：判断前先想清楚这一条约束谁、保护谁。
- 到此停止迭代，直接跑全量；20 份小样用于调试，全量结果另外单独报告其余 28 份留出合同的数字。

## P21：代码审查发现的两处金标准漏标，以及一个租户隔离漏洞

- 金标准漏标  - 4 份"我方为甲方"的合同，对方在构造台账里的资质已经过期（台账生成时故意放了过期样本，合同生成器却没考虑）；三家规范都把资质有效写成硬性要求，agent 查台账后报出是对的，却被算成误报。
  - 甲方视角的"安全"责任限制条款把"侵犯知识产权、违反保密义务"等排除在上限之外，例外对我方同样适用，等于我方赔偿可能无上限，违反华信第十四条、云启第十一条。21 份合同带这一条。
- 解决：不改合同正文（这样可以用同一批 agent 输出重新判分），在评测集里加 `acceptable` 标注，这类意见不算误报也不算检出。`scripts/analyze_review.py --rescore` 从 trace 重算，不调用 API。全量精确率 68.0% → 71.3%（高/中 72.6% → 76.1%，留出集 81.1% → 82.4%）；检出、类型、依据、干净合同误报率不变。
- 租户隔离漏洞`scope_sql` 靠同名 CTE 遮蔽真实表，但 `main.suppliers`、`"main"."purchase_history"` 这种带 schema 的写法会直接解析到真实表，读到别的租户。合同正文是用户输入，注入一句话就可能诱导模型这么写。修复：带 schema 前缀的 SQL 一律拒绝，补了 5 个回归用例。检查过已有运行的全部 trace，agent 从未写过这种 SQL，已登记数字不受影响。

## P22：DeepSeek 把审查结果写成了不合法的 JSON，三份合同直接兜底

- 现象：DeepSeek 20 份小样（runs/review-ds-s20-fc3013）有 3 份"没调用终止工具"就结束，检出率只有 77.8%。
- 怎么发现的：看兜底那一步的输出，内容就是完整的 submit_review 参数，但 `json.loads` 报"缺逗号"。定位到字符串里直接写了英文双引号：`"…将使我方"逾期视为合格"…"`。适配器按设计把不合法的参数降级成文本，agent 就当成没提交。
- 解决：两层。①从源头：DeepSeek 官网 Tool Calls 指南说明 strict 模式是 Beta 功能，要走 `https://api.deepseek.com/beta` 并在每个函数上设 `strict: true`；我们的工具定义本来就满足"全部 required、additionalProperties: false"，适配器在全部工具都是 strict 时自动切 Beta 端点。②兜底：解析失败时做一次保守修复，字符串里的 `"` 后面不是 `, } ] :` 或结尾，就当作正文引号转义。对样本里 3 份真实失败全部修复成功。修完后这两份重跑（runs/review-ds-strict-smoke-2a3bcb）4/4 检出。

## P23：长对话小样里，压缩根本没触发；全量历史答对了却被判错

- 现象：3 组长对话小样（已中止，不计入结果）的前 20 轮里，"摘要压缩"和"全量历史"表现一模一样；全量历史在第 8 轮被判错。
- 根因：①8 轮对话的全量历史只有约 5600 字，低于 6000 字的压缩预算，压缩从未发生，这样比较没有意义；②第 8 轮的回答是"除已谈妥的第六条外，其余为第四条、第七条、第一条"，完全正确，但判分规则只要回答里出现第六条就判错。
- 解决：压缩预算降到 3000 字（约在第 4–5 轮触发）；列清单题的判分忽略"除……外 / 已谈妥 / 不再 / 无需"这类排除语境里提到的条款，补了回归测试。小样重跑。
- 第二次小样（runs/review-longdialog-s3-235a43）又发现：8 次摘要压缩里 4 次报错，退回了规则台账。记下错误信息后离线重放，原因是"字符串未结束"，Haiku 的自适应思考 token 也计入 `max_tokens`，1500 不够，JSON 被截断。上限改为 4000，并对 `stop_reason == max_tokens` 明确报错；重放 3 组对话 0 错误、0 补录。顺带修了统计：规则兜底那次不再计入"模型摘要漏项补录"。
- 全量跑完（runs/review-longdialog-full-1d77c3）后，第 8 轮三种方式都只有 4–5/12，逐条对照发现又是判分问题：①12 组里 7 组，首轮被谈妥的第 2 条意见和另一条意见在同一条款上，这个条款本来就该继续列出，规则却要求不列；②"第0轮第1条""第2条意见"这类意见编号被当成合同条款。修正标准答案生成与条款抽取（补了回归测试），用 `scripts/rescore_longdialog.py` 从 trace 重算，不调 API：改判 12 轮，全部由错改对；"只留最近 2 轮"仍是 0/12。原始汇总保留在 `summary_original.json`。


## P24：多 Agent / 记忆分支的代码审查，会"静默漏审"的格式问题、会退化的用户决定、能放过错答案的判分

- 审查方式：合并前用独立的审查代理通读整个分支，另用假数据写探针复现。
- 严重：多 Agent 只认"第X条 标题"这种格式，"第一条【价款】"或"一、价款"这类合同一个条款都识别不出，主审的分派被静默丢弃，三个专职组都拿到空内容，最后返回"没有问题"。修复：放宽标题识别（前后端一致）；原文里确有、却没解析出的条款号，或一个条款都没识别出时，回退单 Agent 审全文。修复时还发现回退条件写得太激进，主审常写"缺失（保密条款）"提示缺条款，不该触发回退，改为只看原文里真实存在的条款号。
- 重要：
  - 一个专职组超时会让整份审查失败，现在其余组照常汇总，并注明哪类风险没审；
  - 子 agent 引用了没检索过的编号会被悄悄丢掉，现在记进 invalid_citations；
  - 摘要压缩第二次漏掉"已谈妥"那条时，规则补录会把它退化成"已报"，和"已谈妥的不再列"直接冲突，现在补录沿用上一份摘要的状态；
  - 同一会话的两个追问可能并发改同一份记忆，现在同一会话串行，第二个请求返回 409；
  - 长对话判分：书名号里的法条号（《民法典》第七条）和"你列的第1条"会被当成合同条款，"排除语境"能跨过别的条款把错答案放过。全部收紧，从 trace 重算只改判 1 轮（结论不变）。
- 小问题一并修了：超预算后成批压缩、补录只计一次、没有摘要模型时按纯规则台账、摘要里的立场取最新、首轮反问后"首次审查"标在第一次给意见的那一轮且这一轮走多 Agent、检索与查表分锁。


## P25：难评测集 v2，多 Agent 的三种漏检，以及数据集自己"制造"的合理意见

- 漏检类型（ADR 013）：
  - 原版多 Agent 两次各漏 8–9 处，集中在跨条款组合（66.7%）和临界值（73.3%）。原因有三：
    - 主审从不分派"定义"条款，靠定义构成的组合风险全部漏掉；
    - 定金和违约金分到了不同组，"叠加适用"没人看得到；还有一份合同的保密条款没被分派；
    - 专职组不拿数值去对照规范红线（保密期 2 年、违约金日万分之八、首付款 20%）。
  - 单 Agent 两次共漏 5 处：保密信息被定义限定为甲方信息 ×2、付款与开票互为前提、完整协议条款改写管辖、首付款 20%。
- 改进：定义条款发给各组；漏分的条款按关键词兜底；主审每条都分派；专职组逐项对照红线、结合其他条款看。改进后两次都是 75/75，代价是风险合同上的误报约翻倍，单份花费约 1.75 倍。
- 标准答案修正：改进后的多 Agent 会读定义条款，于是报出了一批"误报"。逐条看下来，大部分是数据集本身的文本引出的合理意见：
  - 生成器给每份合同加了基础定义，"定作物 / 交付成果，指交付的某某"，无意中把知识产权条款的覆盖范围缩窄了。华信规范第二十条就要求图纸、模具归公司，所以审查方指出这一点是对的。
  - 设备类检验期改成从"安装调试合格之日"起算后，合同没写安装期限，审查方指出验收和付款可能被拖延。
  - 标为"对我方有利"的自动续期条款，没约定提前通知不续期，违反三家规范的要求。
- 处理：把这三类补进 acceptable，合同正文不变（全文哈希校验一致），6 次运行用同一份新答案重算，不调 API。修正前后的数字都登记在 numbers.md。修正幅度：
  - 精确率（高/中）各运行升 4–16 个点；
  - 视角错误从 21% 降到 0%（改进后的两次运行），单 Agent 第一次从 10.5% 降到 5.3%；
  - 检出率不变。
- 另外两个工程坑：
  - 生成器遍历集合，顺序随哈希种子变化，每次生成结果不同，改为排序；
  - 4 个全量并行跑到一半时会话退出，进程被一起终止，于是加了 `eval-review --resume`，并用 nohup 启动。
