# ADR 001：PDF 解析器选 docling（关闭 OCR）+ 自写规则

- 状态：已采纳

## 背景

PRD 要求解析时保留表格、标题层级和页码，前端还要能按坐标高亮原文。候选是 docling 和 MinerU。

## 实验

- 夹具 `tests/fixtures/`：
  - `bnu_sample.pdf`：北师大 2025 手册物理页 9、10、166、308、309，涵盖部分标题、法规目录、章节、奖学金金额段落；
  - `upc_sample.pdf`：中石油 2025 手册物理页 11、51、163，涵盖学籍规定开篇（有"暋"乱码）、微专业表格、奖学金条款；
  - `national_sample.html`：教育部令第 41 号的 gov.cn 页面。
- 环境：MacBook（Apple Silicon），CPU 推理，隔离环境 `uv run --isolated --with ...`，脚本 `scripts/parser_spike.py`。

| 项 | docling 2.142.0（do_ocr=False） | MinerU 2.7.6（pipeline 后端） |
|---|---|---|
| 中石油 3 页耗时 | 11.5s（含模型加载） | 152.9s（首次，含模型下载）；热启动后北师大 5 页 43.9s |
| 北师大整本 378 页 | 59.8s，峰值内存 5.2GB | 未跑整本；按 5 页 43.9s 外推约 50 分钟（估计值） |
| 峰值内存（夹具） | 2.2GB | 2.7GB |
| 表格 | 微专业表还原成 5 列 Markdown 表，跨行单元格正确 | 还原成 HTML 表（带 rowspan/colspan），同样正确 |
| 标题层级 | 识别出标题，但全部是 1 级 | 识别出标题，但全部是 1 级（text_level=1） |
| 页码 / 坐标 | 每个元素都有，页码从 1 开始，坐标为 PDF 点（左下原点） | 每个元素都有，page_idx 从 0 开始，坐标归一化到 0–1000 |
| 中石油"暋"乱码 | 保留（夹具 18 处），中文字间有断行空格，段落被版面切成多行 | 已清除，段落完整 |
| 北师大整本乱码 | 0 | — |
| 部署形态 | Python 库，直接 import | 2.x 是命令行加模型下载；最新 4.x 改为本地后台服务 + 遥测 + 默认远程解析 |

另外两点：
- docling 默认开启 OCR，在文字版 PDF 上很慢：378 页 15 分钟没跑完，已中止。改成 `do_ocr=False` 后 60 秒跑完。
- docling 的 HTML 解析会把 gov.cn 页面的导航栏当成正文，抽不到条文。

## 决定

1. PDF 和 DOCX 用 docling，关闭 OCR：速度快约 50 倍，可以直接作为库调用，坐标和页码齐全。
2. 两者都没解决的问题，用自写规则补上（都有单元测试）：
   - 标题层级：按"部分 > 章 > 节 > 条 > 一、 > （一） > 1. > （1）"的编号推断（`headings.py`）；
   - 乱码与断行空格：清除已知的错误字形映射（"暋""暠"），去掉中文字之间的空格（`textclean.py`）；
   - 版面切断的段落：同一页内，上一段没以句末标点结束、下一段也不是新编号，就接回去（`structure.merge_paragraphs`）。
3. 网页不用 docling：用标准库 `html.parser` 按站点的正文容器抽取（`html_parse.py`）。
4. 坐标统一转成左上原点的 PDF 点，前端用 pdf.js 定位。

## 放弃 MinerU 的理由

- 文本质量更干净，但整本手册慢约 50 倍（外推值）。
- 最新版本改成了后台服务加遥测的形态，不符合"少依赖、本地可复现"的要求。
- 它解决的乱码和断行问题，用几十行规则就能补上；层级问题它同样没解决。

## 什么情况下重新考虑

如果之后收进扫描版 PDF（质量报告出现"疑似扫描页"），对那几份单独开启 OCR，或者改用 MinerU，并记入问题日志。

## 代价

- 安装体积：docling 依赖 torch 等，模型缓存约 5GB（`~/.cache/huggingface`，含两次实验）。
- 峰值内存 5.2GB（378 页整本）。
